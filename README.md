# Cloudera to GCP Migration: Automated Execution Architecture

This document covers the technical architecture, execution playbook, and error recovery models for migrating a legacy Cloudera (Hadoop/Hive/HDFS) environment into a modernized Google Cloud Platform ecosystem using native open-source frameworks.

---

## Migration Architecture Summary

The target architecture focuses on decoupling the monolithic Cloudera infrastructure into highly-scalable, managed Google Cloud primitives:

| Component Type | Legacy Cloudera Environment | Target GCP Architecture | Open Source Tooling Applied |
| :--- | :--- | :--- | :--- |
| **Storage Layer** | HDFS (Hadoop Distributed File System) | Google Cloud Storage (GCS) | Hadoop `distcp` + GCS Connector |
| **Compute / SQL Engine** | Apache Hive / Apache Impala | Google BigQuery | Google OS Data Warehouse Migration Tool |
| **Metadata Management**| Hive Metastore (RDBMS Backend) | BigQuery Metastore / Dataproc Metastore | Cloud Storage Hive Tables Sync Framework |
| **Data Integrity Checking**| Manual Checksums / Custom Scripts | Automated Row & Hash Validation | Google OS Data Validation Tool (DVT) |

---

## Blueprint Workflow and Dependency Matrix

To guarantee maximum system state integrity, the migration relies on a strict order of execution:

```
[1. Setup Environment] ──> [2. Cloud Auth] ──> [3. Cloud Infra Provisioning]
                                                          │
                                                          ▼
[6. DVT Row Validation] <── [5. DistCp Storage] <── [4. Metadata & DDL Extraction]
```

1. **Idempotency**: Every phase is designed to be re-run safely if network failures or cluster disconnections interrupt processing mid-way.
2. **Resume Capability**: `hadoop distcp` with the `-update` flag analyzes existing signatures on GCS and skips identical byte structures.

## Prerequisites & Local Setup
Before executing any phase, ensure the following tools are installed and available on your migration gateway node or Cloudera edge node:
1. **Google Cloud SDK (gcloud)**: Certified for authenticating and routing traffic into GCP API endpoints.
2. **Terraform CLI (>= 1.3.0)**: Used to stand up the GCP cloud landing foundations.
3. **Cloudera Clients Installed**: The edge node must have authenticated access to active `hadoop distcp` and `hive` command-line interfaces.
4. **Python (>= 3.8)**: Required to install and run the validation framework.

## Execution Instructions
Follow these steps sequentially to configure your variables, provision infrastructure, stream your data, and execute target schemas.

### Step 1: Clone the Repo and Establish Configurations
First, clone the codebase, construct your folder structure, and configure your parameters inside the `config/` directory.

```bash
# Initialize project workspace directories
mkdir -p config scripts terraform

# Open and customize your configurations (Do not commit these files)
nano config/config.env
nano config/variables.tfvars
```

Ensure your `config.env` matches your cluster endpoints, and your `variables.tfvars` matches your target GCP landing specifications.

### Step 2: Provision GCP Target Landing Infrastructure
Navigate into the `terraform/` workspace to plan, validate, and instantiate your GCS storage systems, BigQuery warehouses, and your Dataproc worker cluster.

```bash
cd terraform/

# Initialize and pull the Google Cloud provider plugins
terraform init

# Validate syntactic configuration soundness
terraform validate

# Review the structural footprint plan before changes apply
terraform plan -var-file="../config/variables.tfvars"

# Apply changes to provision GCP infrastructure
terraform apply -var-file="../config/variables.tfvars" -auto-approve

# (Optional) Verify output metrics generated by the infrastructure pass
terraform output
```

### Step 3: Run the Migration
Return to the root directory and leverage the executable Bash runbook inside `scripts/`. The runbook supports modular phase arguments or sequential complete execution. Ensure you give the script executable permissions:

```bash
cd ../
chmod +x scripts/migration.sh
```

#### Run Option A: Execute Partitions Individually (Recommended for Testing)
Run specific operational segments sequentially to safely isolate errors during initial proof-of-concept windows.

```bash
# Initialize requirements and download validation dependencies
./scripts/migration.sh setup

# Authenticate the local edge terminal context to GCP 
./scripts/migration.sh auth

# Extract Hive schemas and output structural DDL dumps
./scripts/migration.sh schemas

# Execute Apache DistCp to stream raw HDFS layers into GCS Buckets
./scripts/migration.sh data

# Run data-validation cross-checks (Hive vs BigQuery counts)
./scripts/migration.sh validate
```

#### Run Option B: Execute End-to-End Automatically
If your local pipelines are thoroughly verified, fire the automated master sequence to trigger every phase step-by-step from validation to ingestion:

```bash
./scripts/migration.sh all
```

## Cleanup and State Teardown

To purge temporary state records, localized tracking metadata logs, and clear cache structures:

```bash
# Removes locally generated schema .ddl and tables.txt files safely
rm -f scripts/*.ddl scripts/tables.txt
```

To entirely destroy and tear down the infrastructure landing zones created inside your Google Cloud environment (Warning: This action deletes data inside target GCS buckets and BigQuery schemas):

```bash
cd terraform/
terraform destroy -var-file="../config/variables.tfvars" -auto-approve
```
